# Native build: hardware checks on 12 September 2026

Overall result: **PARTIAL**. This records specific passing checks on one LS420D,
not completion of the full hardware test protocol or approval to publish firmware.
The unit is identified here as pilot A. Its board revision was not independently
recorded during this run. Earlier UART work damaged R106; these tests do not
certify the damaged area. No UART contact was used in this run.

## Configuration-only update

With the generic image hash unchanged, a newly generated private companion
changed only the configured hostname. The 2,624-byte companion transferred at
22:03:53 UTC; SSH subsequently confirmed the new name in both UCI and the running
kernel. The original 2,112-byte companion was then restored and transferred at
22:05:47 UTC. SSH confirmed the original deployment name after that reboot.

The temporary rsync installation and RAM restore directories were absent after
reboot, as expected. The generic kernel did not need rebuilding for either
configuration change. This is a positive companion test; it does not replace
absent-companion or malformed-companion testing.

## RTC and Wake-on-LAN

The NAS completed an NTP query through a temporary relay to a public time server.
The query returned stratum 1 and exited successfully. Synchronized UTC was written
to the RTC before arming an alarm for 21:41:00 UTC. The alarm readback was checked
before normal poweroff. External power remained connected.

A magic packet sent at 21:36:32 UTC did not wake the NAS in this setup. The laptop
reported its Ethernet link disconnected. Successful submission to the laptop's
UDP socket does not prove reception by the powered-off PHY. `Wake-on: g` before
shutdown alone is therefore not evidence that wake by magic packet works.

At 21:41:01 UTC the link returned; the TFTP transfers and SSH checks followed.
This establishes one complete RTC-triggered poweroff/wake cycle for the native
image. It does not establish RTC retention after removal of external power.

After wake the alarm was still enabled, now showing the following week's date.
It was explicitly cleared and `alarm_IRQ: no` verified. A deployment using RTC
wake must clear consumed alarms and only arm a new shutdown alarm after verified
time synchronization. This operational policy is not supplied by this test.

## Synthetic pull and restore on both bays

Two identified 1 TB Seagate ST31000520AS test disks each contained an independent
Btrfs filesystem. Their identities were checked privately by serial and UUID,
then confirmed with read-only mounts. Existing files were preserved. A new,
dedicated test directory was written on each disk; neither disk was reformatted.

The generic bring-up image does **not** contain rsync. For this test only, rsync
3.5.0 and its missing dependencies were installed into RAM using verified official
OpenWrt 25.12.5 repository indices. Signature checking was not disabled. The
packages disappeared during the subsequent reboot. This tests the storage path
with that tool version, not a finished backup appliance or persistent package
provisioning.

The NAS initiated `rsync -aHAX --numeric-ids` from a read-only synthetic source
through an SSH tunnel. The fixture contains about 9.5 MiB of deterministic data,
an empty file and directory, names with spaces and Unicode, a hardlink pair,
a symlink, fixed file timestamps and a user extended attribute. Each disk copy
was restored into a separate directory in RAM.

On both disk and restored copies:

- SHA-256 matched the independently prepared fixture inventory for every file.
- The hardlink pair shared an inode and the symlink retained its target.
- The empty directory existed.
- A checksum-enabled rsync dry-run, including ownership, permissions, timestamps,
  hardlinks and extended attributes, reported no changes against the source.

Both filesystems were then unmounted and `hdparm -y` requested standby.
`hdparm -C` reported standby immediately and on a later check while the fan
supervisor remained active. This is a small functional test, not sustained I/O,
a full Btrfs scrub, an ACL-specific fixture or a production backup/restore test.

## Fan observations and remaining limits

The supervisor saw the CPU, PHY and both disks with `fault=0`. At a later idle
check the CPU read 51,573 m°C, the PHY 49,000 m°C and fan state was 1. Both disks
were still asleep. CPU thresholds were 60/65/75 °C.

A separate 90-second CPU workload repeatedly hashed the BusyBox executable. A
supervising loop checked the sensor each second and would stop at 70 °C or a
reported fan-control fault. Ten-second samples rose from 53,743 to 64,593 m°C.
The fan changed from state 0 to state 1 after crossing 60 °C; subsequent samples
reported fault 0. The workload exited normally and was stopped by its cleanup
handler. This establishes a short-load response at the first CPU threshold,
not thermal equilibrium, response at every threshold or physical fan RPM.
No sensor or fan fault was injected.

Still unverified here: mains-loss/cold-start reliability, magic-packet wake,
the full LED/button/USB matrix, sustained memory and storage load, injected
fan/sensor faults, and the absent/malformed companion cases on this exact image.
Repeated GitHub builds and the independent cache-free offline rebuild now
match; see [the reproduction evidence](offline-source-path.md). Reproduction
does not extend the hardware coverage. These limits must not be described as
passing merely because normal boot and the small storage fixture succeeded.
